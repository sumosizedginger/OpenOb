## Severity

**P0/P1: none.** The boundary itself is solid and was genuinely hardened (CLI backdoor closed, workspace internals private, loopback enforced).

**P2 (one, unchanged from E2):** the gateway **process** is still not runnable — `npm run gateway` / `npx openob-gateway` fail with `ERR_MODULE_NOT_FOUND` on a fresh checkout and on the current tree. This is a packaging/runnability gap only: the server library is fully proven under vitest/tests, and no data or security boundary is affected. The report's "binary packaging verified" claim is accurate only for the CLI executable.

## Recommendation

Close the gateway-executable gap before Phase 2 mutation work (it is the harness Phase 2 must be verified through). Smallest coherent fixes:

1. Ship the gateway bin as a JS wrapper that loads the TS source through a TS runtime (`tsx`/`vite-node` as a dependency) — consistent with the repo's TS-source-first resolution; or
2. Repoint `@okw/*` package `exports` to `dist` + keep dist committed or built by `prepare` — larger blast radius (affects the vitest alias workflow), so (1) is preferred.
   Add one permanent process-spawn test for `dist/bin/gateway.js` (health 200, 401/200 auth, invalid vault → exit 1, SIGTERM → clean exit), mirroring the existing CLI test 20.

Everything else from the Phase 1 closure and the E1-E5 re-audit stands: **one trustworthy OpenOb application boundary; read-only foundation proven; adapters have no backdoor.**
