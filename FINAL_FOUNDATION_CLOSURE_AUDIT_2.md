## 4. Why CI is green despite these

Every gate passes because none of the failing paths are exercised:

- FSA mode: no committed test touches `BrowserFSAVaultStorage` (neither unit nor e2e — the app runs on `MemoryVaultStorage` in tests). The T1/T1a regression is invisible to CI.
- Node recheck window: the committed node-fs tests cover delete-before-write and stale-version-at-entry, not the validation→rename window.
- Discard: Probe F and the e2e H3 test assert restore-to-baseline where baseline == the initial snapshot (the restore is "correct" only because baseline never advanced); neither does a prior durable save B, a slow in-flight write with a real 3200 ms overlap, a reopen race, or an external edit during restoration.
- Index guard: no committed test forces equal `modifiedAt` or an old-path upsert after rename/delete.

## 5. Classification of the new H2 remediation itself

The intent (re-verify at commit time) is right, but the implementation is wrong in three independent ways:

1. **FSA token built from `newHash`** — guarantees a false conflict on every update (and the null-create branch is self-defeating because `getHandleForPath(create=true)` materializes the target first). **P1 WEB — FSA mode cannot create or update any note.**
2. **Node recheck uses stale `existingHash` + fresh stat** — cannot detect same-size/same-mtime content replacement. **P1 — silent overwrite of an external change.**
3. **Both recheck `catch` blocks swallow unexpected errors and proceed to commit** — fail-open. **P1 — a safety check that cannot fail closed is not a safety check.**

Plus the discard restoration (H3) is a new P1 class: stale-baseline restore (T4), old-pump interference with a reopened session (T5), and unversioned `force: true` restoration (T6).
