All boundary-relevant criteria still hold: no P0/P1 on the boundary; web regression green (9/9 e2e, 212 unit); adapters cannot bypass `OpenObWorkspace`; read-only guarantee proven (byte-identical vault under the adversarial matrix); path traversal blocked; auth real (now timing-safe); loopback default; search/index reuse correct; single-authority docs truthful; CI green.

The E2 runnable-process gap is the **only remaining open P2** and does not undermine the boundary. Recommendation:

1. Close E2 before Phase 2 mutation work starts — the gateway process is the harness Phase 2 writes will be verified through. Minimal fix directions: (a) add a JS bin wrapper that runs the TS source through a TS runtime (`tsx`/`vite-node` — add as a devDependency and have `bin` point at a tiny `node_modules`-independent wrapper, or ship `tsx` as a dependency); or (b) add `build` scripts to all `@okw/*` packages (emit `dist`), repoint package `exports` to `dist`, and wire the root `npm run build` to emit them; then `npx openob-gateway` works as documented. (a) is the smallest coherent slice for a monorepo that resolves everything through TS sources today.
2. Add a permanent **process-level** test (spawn the bin against a temp vault: health 200, 401 without token, 200 with token, invalid vault → exit 1, occupied port → exit 1, SIGTERM → clean exit, no junk left).
3. Update `EXTERNAL_ACCESS_PHASE1_REPORT.md` to describe what is actually runnable until then (or fix (1) and keep the report).

P2 does not block the Phase 2 _architecture_ work (mutation service methods can be built on `OpenObWorkspace` now), but the runnable gateway must exist before Phase 2 endpoints can be verified end-to-end. Everything else from the Phase 1 closure stands: **the boundary is one trustworthy OpenOb application boundary; the read-only foundation is proven.**
